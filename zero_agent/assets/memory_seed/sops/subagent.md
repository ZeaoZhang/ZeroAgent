# 子 Agent 调用 SOP

## 目的与入口

子 Agent 是独立 ZeroAgent CLI 进程，使用任务目录中的文件接收任务、交付结果。主 Agent 负责选任务、提供足够上下文、检查运行状态、验收结果并整合；子 Agent 负责完成分配范围内的工作。

标准入口是通过 `code_run` 执行 `zero-agent --task <任务目录>`。当前没有可供模型直接调用的 `subagent_run` 工具；不要把它当成工具名调用。

在 ZeroAgent Desktop 会话里，通过 `code_run` 启动的 `--task` 子 Agent 会自动登记到当前会话的 Active Agents 面板。面板默认收起，点击右侧开关查看。独立终端启动的 CLI 子 Agent 不属于 Desktop 会话，因此不会出现在该面板。

## 何时委托

适合委托：

- 有明确边界、可以独立完成的只读探索、资料整理、单文件或独立模块修改、复核任务。
- 多个任务互不依赖、输入和输出各自独立，主 Agent 能在最后统一汇总。
- 需要隔离长篇材料或重复工作，避免占用主 Agent 的上下文。

不适合委托：

- 很小、几步即可完成，或需要主 Agent 连续做全局判断的任务。
- 多个 Agent 会同时改同一文件、操作同一个浏览器标签或共享键鼠状态。
- 子任务边界无法说清，或结果仍需要主 Agent 重做大部分工作才能使用。

多个子任务只有在彼此独立时才并行。为每个 Agent 分配单独的任务目录、输入和产物路径；若任务有先后依赖，先完成前一项再启动后一项。

## 启动前：写清楚任务单

1. 在项目根目录下为每次调用创建唯一目录：`temp/<task_name>/`。目录名使用短英文或拼音，避免复用旧目录。
2. 启动前先写入 `input.md`。即使任务只有一句话，也要写入文件，不要只依赖命令行参数。
3. 任务单写清目标、必要背景、输入路径、权限边界、交付物和验收标准。不要只写“调查一下”或“帮我处理”，也不要把完整执行步骤塞给子 Agent。
4. 使用绝对路径传递项目文件和产物路径。CLI 的工作目录继承启动方；`--task` 只指定任务文件与输出目录，不会自动切换到任务目录。
5. CLI 优先读取 `input.txt`，只有没有 `input.txt` 时才读取 `input.md`。使用本 SOP 时只保留一个输入文件，避免旧的 `input.txt` 覆盖新任务。

任务单模板：

```markdown
# 任务：<一句话说明>

## 目标
<需要得到什么结果；只描述一个可验收的目标>

## 背景与输入
- 背景：<理解任务所需的最少信息>
- 输入：<绝对路径；没有则写“无”>

## 工作范围与边界
- 负责：<明确模块、文件或问题范围>
- 可以：<允许的读取、修改、命令或外部资料>
- 不可以：<禁止的修改、外发、共享资源操作或额外委托>

## 交付物
- <绝对路径或明确的回复内容>
- 回复中列出结论、关键依据、改动路径和未解决项

## 验收标准
- <可观察、可检查的完成条件>
- <需要保留的兼容性或约束>
```

根据任务删掉不相关的小节，但不要删掉目标、边界、交付物和验收标准。只读探索要明确写“只读，不修改文件”；代码修改要给清楚文件所有权和允许改动范围。需要子 Agent 执行多步且有依赖的工作时，在任务单中说明它可以按项目的 plan SOP 自行规划；不需要替它设计每一步。

## 启动命令

在项目根目录通过 `code_run` 执行：

```bash
zero-agent --task "/绝对路径/到/temp/<task_name>" --verbose
```

- 先确认 `input.md` 已写好，再运行命令。
- `--task` 默认会后台启动并打印 `PID: <数字>`，调用方应很快返回。不要额外加 `--nobg`；`--nobg` 会让调用方等待整个任务结束。
- `--verbose` 用于留下更完整的过程输出，便于主 Agent 检查任务是否走偏。
- 记录任务目录、PID 和启动时间。未看到有效 PID 或命令报错时，视为启动失败；先检查路径、输入文件和 `stderr.log`，修正后再试。

## 运行监控

启动后确认 Active Agents 面板里出现对应任务；`running` 表示正在处理，`waiting` 表示本轮已结束、进程在等待 `reply.txt`，此时没有继续推理。如果是在独立终端启动，则按 PID 和任务目录检查。不要仅凭“命令已返回”推断任务仍在运行，也不要仅凭 PID 曾经打印过就推断它还活着。

结果文件位于任务目录：

- 首轮：`output.txt`
- 后续回复轮：`output1.txt`、`output2.txt`，依次递增
- 每轮完成标记：`[ROUND END]`
- 启动或运行错误：检查 `stderr.log`

`output.txt` 通常在一轮结束时写入；文件暂时没有新内容不等于进程卡住。结合面板状态或进程存活状态判断。需要看进度时，每隔几秒读取最新输出的新增部分即可；主 Agent 空闲时可以持续监察，但不要长时间无条件等待，也不要每次重复读取整个文件。

若需要 Agent 继续一轮：在任务目录写入 `reply.txt`，其中放下一轮指令。子 Agent 消费该文件后写入下一个 `outputN.txt`。没有后续指令时，它最多等待 10 分钟后退出。

干预文件：

- `_intervene`：追加一条立即纠偏的指令。
- `_keyinfo`：在 Agent 到达某一步前补充必要上下文。
- `_stop`：请求当前轮结束后停止；它不是立即杀进程的信号。
- 面板上的 Cancel：停止对应 Desktop 子 Agent 进程；取消主会话也会停止该会话登记的子 Agent。

只在发现具体偏差、缺少关键上下文或用户要求停止时干预。指令应短、具体，并指向遗漏的验收条件。

## 收集与验收

1. 等待子 Agent 状态变为 `completed`、`failed` 或 `cancelled`；若为 `waiting`，读取本轮输出后决定是否写入 `reply.txt`，不要把等待误认为仍在执行。
2. 成功结果应有完整的输出文件和 `[ROUND END]` 标记。退出码为 0 但没有输出文件或结果为空，也不能当作完成。
3. 按任务单逐项检查交付物、证据和边界。代码任务检查改动文件与结果；只读任务检查结论是否能由给出的路径或证据支持。
4. 主 Agent 对结果负责：处理冲突、整合需要的改动，并向用户汇报子任务状态、可用结果和未解决项。不要把子 Agent 的自述当作验收证据。

进程退出但没有完整结果时，先检查 `stderr.log`、所有 `output*.txt` 和任务目录，再判断是启动失败、执行失败还是交付不完整。修正原因后最多重试一次；重试前确认旧进程已结束，并使用新的任务目录，避免两个 Agent 覆盖同一批文件。若仍失败，向用户报告具体阻塞点，不要无限重启或伪报完成。

## Map 模式（同构并行任务）

只有当待处理项目清单已知、每项可以独立处理、且结果格式一致时才用 Map 模式：

1. 主 Agent 先准备每项的独立输入文件和任务目录。
2. 每个子 Agent 只处理分配给它的项目，并写入独立产物。
3. 主 Agent 等待各项结果，按同一验收标准逐项检查，再去重、比较并汇总。

有共享写入、顺序依赖或共同决策时不要并行；由主 Agent 串行安排，或先拆清所有权再委托。
