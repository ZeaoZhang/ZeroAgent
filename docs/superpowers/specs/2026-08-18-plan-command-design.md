# `/plan` Command and Plan SOP Design

> This design was derived from the current ZeroAgent implementation and the reference `../AgentExplore/GenericAgent` implementation. It is a design specification, not the implementation plan.

## Goal

Expose ZeroAgent's existing `TaskMode.PLAN` as a first-class `/plan <task>` command across Desktop, CLI, and TUI, while preserving `TaskContract` as the single source of truth and aligning the Plan SOP with the command-driven lifecycle.

## Decisions

- `/plan <task>` explicitly starts a real Plan task; it is not prompt-only injection.
- Desktop uses a dedicated `POST /session/{sid}/plan` resource endpoint. `/slash/resolve` remains a prompt-resolution API for prompt-based commands.
- Plan completion does not modify code automatically. A verified plan becomes `ready`; the user must explicitly approve execution.
- `/plan` can only start from an idle session. Starting it while a session is running returns a conflict instead of interrupting or replacing work.
- ZeroAgent's `TaskContract` remains authoritative. GenericAgent's legacy `working['in_plan_mode']` and message-scan activation are not copied as state mechanisms.
- The existing `verify_sop.md` remains the verification protocol. `plan_sop.md` is updated to document the public `/plan` entry and the `ready` confirmation boundary.

## Reference Findings

GenericAgent provides useful process and presentation patterns:

- `ga.py` has `enter_plan_mode`, plan progress counting, completion interception, and automatic exit.
- `frontends/plan_state.py` parses common Markdown checkbox forms and renders a plan card.
- `memory/plan_sop.md` defines exploration, `[D]` delegation, `[P]` parallel work, `[?]` conditional branches, Mini verification, and an independent verification phase.

ZeroAgent already improves the state model:

- `core/types.py` defines `TaskMode.PLAN` and immutable `TaskContract`.
- `core/handler.py` owns `enter_plan_mode`, plan progress, and plan prompts.
- `core/completion.py` requires zero remaining plan items plus a valid verification result.
- `core/completion_gate.py` blocks unsupported completion claims.

The implementation must bridge these two systems without regressing ZeroAgent's stronger contract and evidence model.

## Architecture

### Core task initialization

`ZeroAgent.run()` currently creates a fresh Handler for every task. Calling `handler.enter_plan_mode()` before `run()` is therefore insufficient: the next run replaces that Handler and resets the contract.

Extend the task-start contract so callers can initialize the first Handler correctly:

```python
agent.run(
    user_input=task,
    initial_mode=TaskMode.PLAN,
    plan_path=plan_path,
)
```

`AgentRunner.put_task()` carries the same optional fields through its queue:

```python
runner.put_task(
    query=task,
    task_mode=TaskMode.PLAN,
    plan_path=plan_path,
)
```

`ZeroAgent.run()` creates the task contract as follows:

- default call: `TaskMode.OPEN`, no plan path;
- `/plan`: `TaskMode.PLAN`, generated plan path;
- approved execution: `TaskMode.EXECUTING`, same plan path.

`TaskContract.task_id` remains generated by `ZeroAgent.run()`. `plan_verify_status` starts as `missing`. Plan mode still receives the existing 120-turn budget.

### Shared plan workspace helper

Add one shared helper module for all frontends, responsible only for deterministic workspace creation and validation:

```python
create_plan_workspace(root: str, task: str) -> PlanWorkspace
```

The helper:

1. derives a filesystem-safe slug from the task;
2. caps the slug length;
3. prevents traversal and absolute-path injection;
4. appends a unique suffix when the directory already exists;
5. creates `plan_<slug>/plan.md` below the session workspace root;
6. writes an initial non-empty skeleton containing the task, exploration section, execution-plan section, and verification section;
7. returns absolute `plan_dir` and `plan_path`.

The initial skeleton contains no fake completed tasks and no implementation claims. The Agent is responsible for replacing the execution-plan section with real `[ ]` items.

### Desktop session state

Extend `desktop_bridge.Session` with persisted metadata:

```python
plan_path: Optional[str] = None
plan_status: Literal[
    "inactive", "planning", "ready", "executing", "failed", "cancelled"
] = "inactive"
plan_task: str = ""
```

Persist and expose these fields in:

- `_session_to_persistable()`;
- `_session_from_persisted()`;
- `AgentManager.snapshot()`;
- `session-state` WebSocket notifications.

The live `TaskContract` remains authoritative while an Agent task is running. Session metadata makes the state visible and recoverable across Desktop restarts.

### Desktop API

Add:

```text
POST /session/{sid}/plan
POST /session/{sid}/plan/execute
```

`POST /session/{sid}/plan` request:

```json
{"task": "实现用户头像上传"}
```

Behavior:

1. validate the session and non-empty task;
2. reject `running` sessions with HTTP 409;
3. reject an existing `planning`, `ready`, or `executing` plan with a descriptive conflict;
4. create the plan workspace;
5. persist `plan_task`, `plan_path`, and `plan_status="planning"`;
6. submit the task through `AgentRunner.put_task(..., task_mode=PLAN, plan_path=...)`;
7. if task submission fails, restore the previous session metadata and remove only the newly created workspace;
8. emit a plan-aware session state notification;
9. return the session, plan path, and accepted task metadata.

`POST /session/{sid}/plan/execute` behavior:

1. require `plan_status="ready"`;
2. reject running sessions and missing plan files;
3. set `plan_status="executing"`;
4. submit an execution prompt that names the approved `plan_path` and preserves the original task;
5. initialize the task with `TaskMode.EXECUTING` and the same plan path;
6. if execution submission fails, restore `plan_status="ready"`;
7. emit the updated session state.


When a PLAN task terminates, `AgentManager.run_agent_turn()` checks the live handler contract and verification state. It changes `plan_status` to `ready` only when the task has a verified completion certificate with zero remaining plan items. Failed and cancelled terminal events retain the plan path and use `failed` or `cancelled` status.

### Desktop UI

- Add `/plan [task]` to `LOCAL_SLASH_COMMANDS`.
- Add the command to the bridge command list so it appears in `/help` and command completion even when the bridge has not loaded other commands.
- Add `startPlan()` and `executePlan()` methods to `za-web.js`.
- Add a `planStatus`/`planPath` projection to the local session state.
- Route `/plan` in `handleSlash()` to the dedicated API, not `runAgentSlash()`.
- Render an active Plan card using the existing plan rendering style.
- When the state becomes `ready`, display the plan path and an explicit “执行计划” action. No execution request is sent until the user activates it.
- Preserve existing `/help`, `/resume`, `/continue`, and prompt command behavior.

The existing `kind === 'plan'` renderer may remain for ACP compatibility, but the bridge must not rely on it as the only Plan state channel. Plan status must also be available through session snapshots and state notifications.

### CLI and TUI

Register `/plan` in the shared slash command surface, but do not make `handle_command()` mutate a pre-run Handler. The CLI/TUI command boundary must call the shared plan workspace helper and then invoke `agent.run()` with `initial_mode=TaskMode.PLAN` and `plan_path`.

The existing TUI `plan_state.py` integration continues to read the live `TaskContract`. It may use persisted plan metadata only for display after a task has become `ready`; persisted metadata must never independently activate Plan Mode.

## State machine

```text
inactive
  └─ /plan <task>
       └─ planning
            ├─ plan verified
            │    └─ ready
            │         └─ user confirms execution
            │              └─ executing
            ├─ failed
            └─ cancelled
```

No automatic code execution occurs at `ready`. This is the safety boundary between planning and modification.

## SOP changes

Update `zero_agent/assets/memory_seed/sops/plan_sop.md`:

- document `/plan <task>` as the public entry;
- retain `code_run(handler.enter_plan_mode(...))` for internal/subagent compatibility;
- define the generated `plan_<slug>/` artifact layout;
- require exploration before plan writing;
- retain `[D]`, `[P]`, and `[?]` semantics;
- require Mini verification after every step;
- require `verify_context.json`, `evidence.json`, `result.md`, and a literal `VERDICT` line;
- define `ready` as “plan verified, awaiting user execution approval”;
- prohibit implementation changes before the explicit execution approval;
- require a final zero-`[ ]` plan scan;
- keep the existing `verify_sop.md` reference and make its path explicit as `zero_agent/assets/memory_seed/sops/verify_sop.md`.

Update user-facing command help or quickstart documentation with:

```text
/plan <task>       创建并运行一个可验证的计划流程
```

Do not create a second plan SOP. The existing `verify_sop.md` is the verification source and only needs consistency checks if implementation reveals a mismatch.

## Error handling and invariants

- Empty or whitespace-only task: HTTP 400 / CLI usage message; no directory is created.
- Running session: HTTP 409 / CLI message; current task is not cancelled.
- Existing active plan: HTTP 409 with the existing plan path; no second plan is created.
- Invalid slug or filesystem failure: return a typed error and remove only the newly created temporary directory.
- Plan directory must remain below the session workspace root.
- Plan status changes and session persistence occur under the existing manager lock.
- A `ready` plan cannot be executed without a plan file and verification status.
- A normal prompt cannot bypass a `ready` plan into code execution; it must use the explicit execute action.
- Existing user modifications in unrelated files must not be overwritten by the implementation.

## Verification strategy

Core tests:

- initial PLAN and EXECUTING contracts are created by `ZeroAgent.run()`;
- Runner queue fields reach `ZeroAgent.run()`;
- the shared workspace helper handles empty, Unicode, long, duplicate, and traversal-like task names;
- existing plan completion and evidence gates remain unchanged.

Bridge tests:

- successful plan creation and accepted task response;
- empty task, running session, duplicate plan, missing session, and filesystem failure;
- state notification and snapshot fields;
- `ready` transition only after valid verification;
- execute endpoint rejects non-ready plans and starts EXECUTING only after approval;
- persistence and reload of plan metadata.

Frontend tests:

- `/plan` appears in command completion;
- `/plan <task>` calls the dedicated API;
- ready state renders an execution affordance;
- execution is not sent before explicit user action;
- existing local commands and backend prompt commands remain unchanged.

Smoke verification:

1. start the Desktop bridge;
2. call `POST /session/{sid}/plan` with a real session;
3. verify the response, created directory, `plan.md`, and running state;
4. exercise empty-task and running-session errors;
5. complete a fixture plan with valid verification artifacts;
6. verify `ready` state;
7. confirm execution does not start until `/plan/execute` is called;
8. call `/plan/execute` and verify the task starts with `TaskMode.EXECUTING`.

## Non-goals

- No rewrite of the existing Agent loop or evidence model.
- No copy of GenericAgent's legacy `working`-based Plan state.
- No automatic code modification after planning.
- No new independent verification protocol.
- No unrelated refactor of the large Desktop JavaScript file.
